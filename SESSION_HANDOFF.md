Срез: 2026-11-10. Репозиторий `/Users/alex/study/p2p_sharing`, GitHub — `Bunsans/p2p_sharing`, ветка — `feat/payment-core`. Общение на русском; режим Ponytail full: минимальное полное изменение с проверкой денежной логики и конкуренции.

## Подтверждено пользователем

- Python/Django + PostgreSQL. Основного backend пока нет; платёжное приложение разрабатывается независимо. Итоговое подключение остаётся в общей сборке и БД, без отдельного платёжного сервиса или обязательного брокера.
- Деньги — целые копейки, округление до ближайшей копейки, половина вверх (HALF_UP). Частичные возвраты считаются накопительно от исходных долей; правило закреплено в принятом [ADR-0005](docs/adr/0005-money-rounding.md).
- Основной способ разработки и проверок — Docker Compose, без необходимости поднимать PostgreSQL на хосте.
- Рабочая бизнес-модель уже обсуждена. Повторный выбор стека, округления и интервью обо всей модели не нужны. Подтверждения провайдера и обязательств заказчика остаются отдельными внешними условиями.

Снимок расчёта содержит отдельные начисления аренды и залога. Ссылки на бронь и участников — непрозрачные строки до 128 символов; идентификаторы расчётов, начислений, попыток и команд — UUID. Это локальный рабочий контракт, ещё не совместная интеграция с основной командой.

`start_payment` принимает уже проверенные вызывающим backend `actor_ref` и `handover_allowed`. Будущий backend должен держать блокировку брони и внешнюю транзакцию через вызов; модуль дополнительно проверяет арендатора, версию и денежное основание. Публичного HTTP API для произвольного пользовательского ввода нет.

`reserve_money` аналогично принимает доверенное `decision_allowed`, автора и версионированное основание. Полномочия, согласие сторон/администратора или факт выдачи проверяет будущий backend. Локальный сервис проверяет связь `settlement_id`/`payment_id`, назначение и денежные лимиты; получатель следует из снимка участников. `basis_ref` глобально идентифицирует одно неизменяемое денежное решение, поэтому для аренды и залога нужны разные ID. `command_id` уникален внутри команд решений, отдельно от команд оплаты. Точный контракт и пример — в README.

`start_outgoing(*, command_id, settlement_id, reservation_id, actor_ref, expected_terms_version, execution_allowed)` явно создаёт попытку исполнения существующего резерва. Авторизацию исполнения/повтора выполняет доверенный backend; сервис проверяет связь с расчётом, версию, успешную исходную оплату с внешним ID и scope `simulator/test/local`. `reserve_money` не запускает исполнение автоматически. Новое решение, резервы и первые попытки при необходимости объединяются внешней `transaction.atomic()` вокруг `reserve_money` и `start_outgoing` для каждого ненулевого резерва; пример — в README.

Резервы постоянные, без состояния банковской операции. Тайм-аут, перезапуск, отказ и успех исходящей попытки их не снимают; исполненная сумма остаётся учтённой тем же резервом без второго расхода. Не добавлять произвольное освобождение возврата: для исходных долей 3/1 три возврата по копейке дают 1/0, 1/0, 0/1; удаление второго нарушит накопительные доли оставшихся. Связь `previous_refund` фиксируется при резервировании, поэтому worker не запускает последующий возврат до успеха предыдущего, даже если у предыдущего нет команды либо его попытка отменена/неизвестна. Две части залога имеют независимые результаты; банковский порядок их исполнения не подтверждён.

Повтор исходящего `command_id` сохраняет прежнюю попытку, изменённые параметры конфликтуют. Новый ключ при `pending`/`unknown`/`succeeded` возвращает ту же попытку. Только подтверждённый `canceled` и новая авторизованная команда допускают новую попытку с новым ключом провайдера; прежний запрос остаётся связан со старой. Область команд исходящих операций отделена от оплаты и решений. Внешние ID исходящих операций уникальны по провайдеру/среде/учётной записи/виду `refund` или `payout`.

`unknown` остаётся открытой попыткой. Без внешнего ID повтор создания прекращается через 23 ч 59 мин от первой потенциальной отправки и требует разбора; при известном ID разрешена сверка чтением. Срок не сбрасывается после перезапуска. Выполненные возвраты в арифметике должны следовать одному накопительному правилу: доля владельца округляется HALF_UP, комиссия получает остаток.

## Запуск и состояние машины

После проверки нового фрагмента Compose работает, app и db healthy. Docker Engine используется через Colima, активный context — `colima`; Compose и Buildx установлены. Если движок остановлен, выполнить `colima start`, затем:

```sh
docker compose up --build --wait
docker compose run --rm app python manage.py check
docker compose run --rm app python manage.py makemigrations --check --dry-run
docker compose run --rm app python manage.py test --noinput
```

Исходники не смонтированы в контейнер: после изменений требуется пересборка. Admin — `http://localhost:8000/admin/`; пользователь автоматически не создавался. Команда создания — в README. Имитатор запускается явно, автоматически денежные команды при старте сервиса не исполняются.

Перед миграцией `0003` остановить старые процессы записи и worker. Она восстанавливает `previous_refund` для старых резервов по времени решений/ID только после проверки сохранённых накопительных долей; при несовпадении останавливается для разбора и не переписывает суммы. После миграции старый код писать резервы не должен. Локальный Compose пересоздаёт app, постоянного worker нет; отдельно запущенную команду worker нужно дождаться/остановить до обновления.

PostgreSQL не публикует порт на хост. Данные находятся в volume `p2p_sharing_postgres_data`; обычный `docker compose down` сохраняет их, `down -v` удаляет. Существующие данные сохранять.

Ранее установленный Homebrew PostgreSQL и остановленный локальный кластер `.postgres/` оставлены на месте; контейнеры их не используют. `.postgres/`, `.venv/`, `.env*`, сборочные артефакты и `__tmp_prompt.md` исключены из Git. Первый запуск Colima потребовал загрузки образа; сейчас движок и базовые контейнерные образы уже подготовлены. Повторять установку окружения с нуля не требуется.

## Следующий шаг

Продолжить независимое ядро [#5](https://github.com/Bunsans/p2p_sharing/issues/5). Актуальные #3/#5/#7/#8 перечитаны при реализации исходящего исполнения; #8 требует одного атомарного решения для обеих частей залога, но независимых результатов исполнения. Новый фрагмент добавляет исходящие попытки, общую сохраняемую очередь, последовательные частичные возвраты и восстановление через явный имитатор. Следующий кандидат — локальные сценарии выдачи/отмены и позднего успеха оплаты по контракту будущего backend. Перед новой реализацией перечитать текущие issues и актуальные результаты проверок.

Пока отсутствуют: банковское исполнение возвратов/выплат, освобождение/пересмотр резервов, сделки провайдера, банковские получатели, webhook и проверка уведомлений, чеки, выдача/отмена и её гонки, денежный расчёт дополнительного времени и вычет оплаченного покрытия, споры и ручные корректировки, гарантированная доставка изменений будущему backend. Расчёт, резервирование и локальная имитация исполнения есть, реального перечисления денег нет. Возврат после выплаты владельцу не финансируется из другого платежа: потребуется отдельный процесс средств площадки. #5 целиком не завершена.

Отсутствие основного backend не блокирует согласованную независимую разработку. Для его подключения предстоит проверить реальные идентификаторы, авторитетные события, общую транзакцию выдачи/отмены и доставку состояний. Политика поздней оплаты устаревшего продления и ряд правил сроков поддержки остаются открытыми в #3.

Банковская интеграция зависит от [#2](https://github.com/Bunsans/p2p_sharing/issues/2): разрешение отдельного залога, полное распределение без уменьшения сумм пользователям на комиссии, малые суммы, фактические сроки и доступ к подходящей песочнице. Обязательства заказчика — [#4](https://github.com/Bunsans/p2p_sharing/issues/4): резерв, чеки, ручные каналы и поддержка. Доступов и новых внешних подтверждений нет; имитация не заменяет банковскую приёмку.
