# Передача контекста: платёжное приложение

Срез: 2026-11-10. Репозиторий `/Users/alex/study/p2p_sharing`, GitHub — `Bunsans/p2p_sharing`, ветка — `feat/payment-core`. Общение на русском; режим Ponytail full: минимальное полное изменение с проверкой денежной логики и конкуренции.

## Подтверждено пользователем

- Python/Django + PostgreSQL. Основного backend пока нет; платёжное приложение разрабатывается независимо. Итоговое подключение остаётся в общей сборке и БД, без отдельного платёжного сервиса или обязательного брокера.
- Деньги — целые копейки, округление до ближайшей копейки, половина вверх (HALF_UP). Частичные возвраты считаются накопительно от исходных долей; правило закреплено в принятом [ADR-0005](docs/adr/0005-money-rounding.md).
- Основной способ разработки и проверок — Docker Compose, без необходимости поднимать PostgreSQL на хосте.
- Рабочая бизнес-модель уже обсуждена. Повторный выбор стека, округления и интервью обо всей модели не нужны. Подтверждения провайдера и обязательств заказчика остаются отдельными внешними условиями.

## Что уже реализовано

| Область | Состояние |
| --- | --- |
| Расчёты | `payments/calculations.py`: наценка 20% к базе владельца, HALF_UP, накопительный частичный возврат, распределение залога, количество суммарных дополнительных получасов. |
| Хранение | `payments/models.py`, миграция `0001_initial`: Settlement, Charge, PaymentAttempt, PaymentRequest, ProviderCommand, ProviderObservation. Защищённые связи, ограничения сумм/статусов и уникальности. |
| Команды backend | `payments/services.py`: `prepare_settlement`, `start_payment`. Снимок условий, проверка доверенного арендатора и версии, повтор бизнес-ключа, сохранение попытки и задания атомарно. |
| Исполнение | `payments/worker.py`: короткий захват с lease, вызов вне транзакции, прежние тело и ключ при повторе, сверка известного внешнего ID, сохранение позднего ответа без отката нового результата. |
| Имитация | `payments/simulator.py` и `run_payment_worker --simulate --limit 100`: детерминированный локальный результат; сетевой адаптер банка отсутствует. Worker выбирает только `simulator/test/local`. |
| Admin | Просмотр истории без добавления, изменения или удаления денежных записей даже суперпользователем. |
| Окружение | Python 3.12, Django 5.2, psycopg 3; `pyproject.toml` и `uv.lock`. `testproject` — локальный проект подключения. Dockerfile, Compose с PostgreSQL 17 и healthcheck обоих сервисов. |

Снимок расчёта содержит отдельные начисления аренды и залога. Ссылки на бронь и участников — непрозрачные строки до 128 символов; идентификаторы расчётов, начислений, попыток и команд — UUID. Это локальный рабочий контракт, ещё не совместная интеграция с основной командой.

`start_payment` принимает уже проверенные вызывающим backend `actor_ref` и `handover_allowed`. Будущий backend должен держать блокировку брони и внешнюю транзакцию через вызов; модуль дополнительно проверяет арендатора, версию и денежное основание. Публичного HTTP API для произвольного пользовательского ввода нет.

`unknown` остаётся открытой попыткой. Без внешнего ID повтор создания прекращается через 23 ч 59 мин от первой потенциальной отправки и требует разбора; при известном ID разрешена сверка чтением. Срок не сбрасывается после перезапуска. Выполненные возвраты в арифметике должны следовать одному накопительному правилу: доля владельца округляется HALF_UP, комиссия получает остаток.

## Что проверено

- 56 тестов прошли на PostgreSQL 17 локально и затем внутри Docker: суммы/копейки, повторные и конкурентные команды, rollback, потеря ответа, истечение lease и окна идемпотентности, устаревшие ответы, неправильные результаты провайдера, права Admin.
- Миграции применяются с нуля; `makemigrations --check --dry-run` и Django system check проходят. Python-пакет собирается с приложением, миграцией и management command.
- Пример оплаты из README проверен до `succeeded` и повторного получения той же операции в локальном проекте. Контейнерный management command проверен тестом; отдельный ручной запуск всего heredoc-примера README внутри Docker не выполнялся.
- Docker-образ собран из lockfile; оба сервиса healthy; Admin и его CSS отвечали HTTP 200 на `127.0.0.1:8000`.
- Ревью выявило некорректное сравнение дат при переводе часов: исправлено нормализацией UTC, добавлен тест. Также проверены неверные типы статуса и длина внешнего ID ответа имитатора.

С момента последнего успешного контейнерного прогона бизнес-код не менялся; подготовка этой передачи обновляет только документацию. Для следующих изменений запускать соответствующие проверки после пересборки образа.

## Запуск и состояние машины

На момент передачи Compose работает, оба сервиса healthy. Docker Engine запущен через Colima, активный context — `colima`; Compose и Buildx установлены. Если движок остановлен, выполнить `colima start`, затем:

```sh
docker compose up --build --wait
docker compose run --rm app python manage.py check
docker compose run --rm app python manage.py makemigrations --check --dry-run
docker compose run --rm app python manage.py test --noinput
```

Исходники не смонтированы в контейнер: после изменений требуется пересборка. Admin — `http://localhost:8000/admin/`; пользователь автоматически не создавался. Команда создания — в README. Имитатор запускается явно, автоматически денежные команды при старте сервиса не исполняются.

PostgreSQL не публикует порт на хост. Данные находятся в volume `p2p_sharing_postgres_data`; обычный `docker compose down` сохраняет их, `down -v` удаляет. Существующие данные сохранять.

Ранее установленный Homebrew PostgreSQL и остановленный локальный кластер `.postgres/` оставлены на месте; контейнеры их не используют. `.postgres/`, `.venv/`, `.env*`, сборочные артефакты и `__tmp_prompt.md` исключены из Git. Первый запуск Colima потребовал загрузки образа; сейчас движок и базовые контейнерные образы уже подготовлены. Повторять установку окружения с нуля не требуется.

## Следующий шаг

Продолжить независимое ядро [#5](https://github.com/Bunsans/p2p_sharing/issues/5). Сначала сопоставить актуальные критерии задачи с кодом. Ближайший кандидат — хранение денежных решений и резервов возврата/выплаты с ограничением по исходному платежу и назначению; подтвердить выбранный объём по трекеру, реализовать один завершённый фрагмент с миграциями и конкурентными тестами PostgreSQL. Это рекомендация порядка работ, а не уже реализованная функция.

Пока отсутствуют: модели и исполнение возвратов/выплат и их резервы, сделки провайдера, получатели, webhook и проверка уведомлений, чеки, выдача/отмена и её гонки, денежный расчёт дополнительного времени и вычет оплаченного покрытия, споры и ручные корректировки, гарантированная доставка изменений будущему backend. Расчёт возврата суммы уже есть, перечисление денег — нет. #5 целиком не завершена.

Отсутствие основного backend не блокирует согласованную независимую разработку. Для его подключения предстоит проверить реальные идентификаторы, авторитетные события, общую транзакцию выдачи/отмены и доставку состояний. Политика поздней оплаты устаревшего продления и ряд правил сроков поддержки остаются открытыми в #3.

Банковская интеграция зависит от [#2](https://github.com/Bunsans/p2p_sharing/issues/2): разрешение отдельного залога, полное распределение без уменьшения сумм пользователям на комиссии, малые суммы, фактические сроки и доступ к подходящей песочнице. Обязательства заказчика — [#4](https://github.com/Bunsans/p2p_sharing/issues/4): резерв, чеки, ручные каналы и поддержка. Доступов и новых внешних подтверждений нет; имитация не заменяет банковскую приёмку.
