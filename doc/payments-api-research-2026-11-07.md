# ЮKassa и отдельный залог: проверка API на 7 ноября 2026 года

Уточнения по договорным правилам и осуществимости залога: [повторное исследование от 11 ноября](yookassa-deposit-feasibility-2026-11-11.md). Ниже сохранён первоначальный разбор API с примерами.

Исследование проверяет платёжную модель [ADR-0001](../docs/adr/0001-mvp-payment-scope.md)–[ADR-0004](../docs/adr/0004-rental-and-payment-ownership.md): аренда и залог оплачиваются отдельно, владелец получает оплату аренды при выдаче, залог возвращается либо распределяется после возврата вещи. Использована официальная документация провайдера. Запросы к платёжному API и реальные расчёты не выполнялись.

**Вывод: ЮKassa «Безопасная сделка» остаётся кандидатом для оплаты аренды. Поддержка всей модели отдельного залога публичной документацией не доказана.** Ниже отдельно отмечены факты API, выводы для проекта и вопросы провайдеру. Документ не меняет принятые рабочие правила аренды.

## 1. Какие продукты различать

| Продукт | Назначение и доступ | Значение для проекта |
| --- | --- | --- |
| API кошелька ЮMoney | OAuth2-доступ приложения к кошельку пользователя: `client_id`, пользовательский `access_token`, разрешённые операции. [Авторизация](https://yoomoney.ru/docs/wallet/using-api/authorization/basics) | Это иной договор взаимодействия, чем магазин ЮKassa. |
| Платежи из кошелька | `request-payment` подготавливает операцию, `process-payment` списывает деньги; повтор последнего с теми же параметрами возвращает прежнее состояние. [Процесс](https://yoomoney.ru/docs/wallet/process-payments/basics) | Эти методы сами по себе не подтверждают реализацию сделок и залогов площадки. |
| ЮKassa «Безопасная сделка» | Оплата списывается у плательщика и сохраняется у провайдера до выплаты или возврата; подключение требует договора. [Основы](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/basics) | Основной исследуемый кандидат. Оплата кошельком ЮMoney внутри ЮKassa не требует перехода на Wallet API. |
| ЮKassa «Сплитование платежей» | Площадка и её магазины подключаются к ЮKassa; магазины подписывают договоры. [Основы сплитования](https://yookassa.ru/developers/solutions-for-platforms/split-payments/basics) | Не подтверждает модель выплат обычным физлицам без подключения каждого как магазина. |

## 2. Транспорт, credentials и повтор запросов

Базовый адрес — `https://api.yookassa.ru/v3/`, запросы POST передают JSON. Для безопасной сделки используют HTTP Basic Auth магазина (`shopId:secret_key`), включая выплаты внутри сделки. Обычные выплаты с баланса шлюза используют отдельные `agentId:secret_key`. Нельзя автоматически переносить credentials и баланс одного продукта на другой. [Формат взаимодействия](https://yookassa.ru/developers/using-api/interaction-format), [пример выплаты в сделке](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/quick-start/freelance).

Для POST/DELETE нужен `Idempotence-Key` длиной до 64 символов; рекомендован UUID v4. Повтор одной операции отправляют с прежними данными и ключом. Гарантия провайдера действует **24 часа**; поздний повтор может создать новую операцию. [Идемпотентность](https://yookassa.ru/developers/using-api/interaction-format).

Следствие для реализации: ключ, неизменное тело запроса и время первой отправки нужно сохранять до сетевого вызова; по истечении окна сначала выяснять результат прежней попытки. Это проектное решение, выведенное из указанного ограничения.

## 3. Сделка, оплата, выплата и возврат — разные объекты

| Объект | Основные запросы | Состояние и смысл |
| --- | --- | --- |
| Сделка | `POST /deals`, `GET /deals/{id}`, `GET /deals` | `opened` / `closed`; хранит `balance`, `payout_balance`, `created_at`, `expires_at`. [Сделки](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/deals) |
| Оплата | `POST /payments`, `GET /payments/{id}` | `pending` → `succeeded` или `canceled`; двухстадийная оплата добавляет `waiting_for_capture`. Финальные статусы оплаты не изменяются. [Процесс оплаты](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process) |
| Выплата | `POST /payouts`, `GET /payouts/{id}` | Карта: `pending` → `succeeded` / `canceled`; причина отмены — `cancellation_details`. [Выплаты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payouts) |
| Возврат оплаты | `POST /refunds`, `GET /refunds/{id}` | Самостоятельный объект с `payment_id`, суммой и результатом; не превращает исходную успешную оплату в отменённую. [Возвраты](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds), [справочник](https://yookassa.ru/developers/api#refund_object) |

Для реально списываемой оплаты нужен `capture: true`; `waiting_for_capture` означает авторизацию денег с ожиданием списания. `POST /payments/{id}/capture` и `/cancel` относятся к двухстадийной оплате; интернет-платёж можно отменить этим методом только в `waiting_for_capture`. Возврат после списания — другая операция. Возврат пользователя на `return_url` возможен при успехе и неудаче и не доказывает оплату. [Процесс оплаты](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process).

## 4. Ограничения безопасной сделки

**Количество оплат и комиссия.** Одна сделка допускает один платёж в `pending`, `waiting_for_capture` или `succeeded`; после `canceled` можно привязать другой. При создании оплаты `deal.settlements` определяет сумму владельцу; разница между общей оплатой и этой суммой должна превышать эквайринговую комиссию. Комиссию провайдера удерживают из вознаграждения площадки. [Приём оплаты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payments).

**Срок.** Продолжительность сделки настраивается при подключении для площадки: документация API указывает диапазон 1–180 дней. После `expires_at` провайдер закрывает сделку и возвращает оставшиеся деньги плательщику. Срок охватывает весь период от создания сделки, а не только пользование вещью. [Проведение сделок](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/deals). На продуктовой странице указан срок до трёх месяцев и ориентир оборота от 800 000 ₽/месяц; это требует уточнения условий конкретного подключения. [Страница продукта](https://yookassa.ru/secure-deal/).

**Возвраты.** Возвращают только `succeeded`; в безопасной сделке — до выплаты/закрытия. При `fee_moment=payment_succeeded` доступна только доля владельца; при `deal_closed` — также комиссия площадки. Полный возврат требует баланса магазина для невозвращаемых расходов эквайринга. Частичный возврат передаёт общую сумму в `amount`, уменьшение доли владельца — в `deal.refund_settlements`; после него должно хватать на допустимую выплату. [Возвраты в сделке](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/refunds).

**Выплаты.** Успешная выплата закрывает сделку автоматически. Для российских карт физлиц опубликованы пределы: 1–150 000 ₽ за выплату, до 20 выплат в сутки и 1 500 000 ₽ в месяц на карту. Бизнес-карты не подходят. [Выплаты в сделке](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payouts). Поля `final_deal`/`final` в прочитанных актуальных инструкциях нет; примеры содержат `deal.id`. Управление закрытием через такой флаг **не подтверждено**; в проектный контракт его включать нельзя без проверки справочника/провайдера.

**Мелкие суммы.** Общий частичный возврат — от 1 ₽; остаток после возврата должен быть 0 ₽ либо минимум 1 ₽. Возврат идёт на исходное платёжное средство. [Общие ограничения возвратов](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds). Следствие: компенсация или возвращаемый остаток 0,50 ₽ требуют согласованного отдельного порядка; самовольное округление меняет утверждённый денежный итог.

## 5. Примеры для оплаты аренды

Это сокращённые иллюстрации формы API с вымышленными идентификаторами. Суммы соответствуют ADR: владелец получает 800 ₽, арендатор оплачивает 960 ₽, комиссия площадки — 160 ₽ до расходов. Пример залога намеренно не представлен как рабочий запрос.

Создать сделку: `POST /deals`.

```json
{
  "type": "safe_deal",
  "fee_moment": "deal_closed",
  "description": "rental:37:base",
  "metadata": {"rental_id": "37", "purpose": "rent"}
}
```

Ответ содержит созданный `id`, `status: "opened"`, `expires_at` и оба баланса. Полученный ID передаётся в оплату. [Создание сделки](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/deals).

Создать оплату: `POST /payments`.

```json
{
  "amount": {"value": "960.00", "currency": "RUB"},
  "capture": true,
  "confirmation": {
    "type": "redirect",
    "return_url": "https://example.com/rentals/37/payment"
  },
  "description": "Аренда 37",
  "deal": {
    "id": "<deal_id>",
    "settlements": [
      {"type": "payout", "amount": {"value": "800.00", "currency": "RUB"}}
    ]
  },
  "metadata": {"rental_id": "37", "purpose": "rent"}
}
```

Один из возможных первых ответов, сокращённый пример с вымышленным ID и URL:

```json
{
  "id": "<payment_id>",
  "status": "pending",
  "paid": false,
  "amount": {"value": "960.00", "currency": "RUB"},
  "confirmation": {
    "type": "redirect",
    "confirmation_url": "https://example.com/provider-confirmation"
  }
}
```

`pending` означает необходимость дождаться результата, а не выдать вещь. Ссылку берём из фактического ответа провайдера; после подтверждения сверяем тот же `payment_id`, ожидаемые сумму и валюту. Это адаптация официального сценария с комиссией при закрытии. [Быстрый старт](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/quick-start/advertisement).

Выплата после разрешения основного backend: `POST /payouts`.

```json
{
  "amount": {"value": "800.00", "currency": "RUB"},
  "payout_token": "<owner_card_synonym>",
  "description": "Аренда 37: выплата владельцу",
  "deal": {"id": "<deal_id>"},
  "metadata": {"rental_id": "37"}
}
```

Ответ содержит ID выплаты, текущий статус и сведения о назначении. Карточный синоним получает виджет провайдера. Для безопасной сделки `account_id` виджета — `shopId`, для обычных выплат — `agentId`. [Выплата через виджет](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/quick-start/freelance), [параметры виджета](https://yookassa.ru/developers/payouts/making-payouts/bank-card/using-payout-widget/implementing-widget).

Полный возврат **до выплаты**, `POST /refunds`:

```json
{
  "payment_id": "<payment_id>",
  "amount": {"value": "960.00", "currency": "RUB"},
  "description": "Передача аренды 37 отменена"
}
```

Частичный возврат 480 ₽, уменьшающий долю владельца на 400 ₽:

```json
{
  "payment_id": "<payment_id>",
  "amount": {"value": "480.00", "currency": "RUB"},
  "deal": {
    "refund_settlements": [
      {"type": "payout", "amount": {"value": "400.00", "currency": "RUB"}}
    ]
  }
}
```

Возврат имеет собственный `id`, `status`, `payment_id`, `amount`; пример успеха — `status: "succeeded"`. Оба примера предполагают `fee_moment=deal_closed`. [Возвраты в сделке](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/refunds).

## 6. Что это означает для отдельного залога

Следующие положения — **выводы исследования**, а не обещания провайдера:

| Сценарий проекта | Вывод из опубликованных ограничений |
| --- | --- |
| Независимые списания аренды и залога | Одна сделка для обоих не подходит. Разные сделки — гипотеза, которую должен одобрить провайдер. Каждая доплата за время также требует отдельного расчёта. |
| Залог 3 000 ₽ без наценки; возможная компенсация 3 000 ₽ | Стандартное требование положительной разницы между оплатой и выплатой мешает выплатить всю сумму. Нельзя считать баланс для возвратов доказательством возможности субсидировать таким же способом выплату компенсации. |
| Компенсация 500 ₽, возврат 2 500 ₽ | Кандидат последовательности: сначала успешный частичный возврат остатка, затем выплата компенсации. Обратный порядок конфликтует с закрытием сделки при выплате. Требуются подтверждение сумм `settlements` и доказательство финансирования всех комиссий площадкой. |
| Претензий нет | Нужен полный возврат залога; проверить резерв для расходов и отсутствие собственного дохода площадки. |
| Спор после `expires_at` | Нельзя обещать бессрочное хранение. Пригодность согласованных 14 суток аренды плюс 7 суток запаса проверяется по фактическому сроку сделки. |
| Возврат уже выплаченной аренды | Предусмотренный ADR ручной процесс площадки остаётся необходимым; первоначальный payout не становится отменённым. |

Основания таблицы: [ограничения оплаты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payments), [порядок выплат](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/basics), [закрытие сделки](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/deals), [ADR-0003](../docs/adr/0003-cancellation-and-refunds.md).

## 7. Уведомления и ошибки

Для безопасной сделки доступны `payment.waiting_for_capture`, `payment.succeeded`, `payment.canceled`, `refund.succeeded`, `payout.succeeded`, `payout.canceled`, `deal.closed`. Отдельное событие `refund.canceled` в опубликованной таблице отсутствует. При HTTP Basic Auth подписки задают в кабинете; endpoint — HTTPS на порту 443/8443, TLS ≥1.2. Формат — `{"type":"notification","event":"payment.succeeded","object":{...}}`. [Уведомления](https://yookassa.ru/developers/using-api/webhooks).

Подтверждение доставки — HTTP 200; иначе провайдер повторяет доставку до 24 часов с момента события. Документированный способ проверки подлинности — сверить актуальный объект через API и/или IP отправителя; HMAC-схема на этой странице не описана. Проектное следствие: обработка должна выдерживать дубли, а окончательное состояние денег нельзя выводить только из непроверенного JSON уведомления. [Проверка уведомлений](https://yookassa.ru/developers/using-api/webhooks).

HTTP 200 с `pending` не означает завершения операции. При `canceled` анализируют причину; новая попытка после её устранения получает новый ключ. При сетевом сбое или HTTP 500 результат неизвестен: повторяют прежний запрос с прежним ключом либо читают объект GET. [Обработка ответов](https://yookassa.ru/developers/using-api/response-handling/recommendations). После 30 секунд без определённого результата ЮKassa может вернуть 500. [Формат взаимодействия](https://yookassa.ru/developers/using-api/interaction-format).

Ошибки: 400 `invalid_request`, 401 `invalid_credentials`, 403 `forbidden`, 404 `not_found`, 429 `too_many_requests`, 500 `internal_server_error`. Ошибка может содержать `id`, `description`, `parameter`. При 429 уменьшают частоту; при продолжающихся 500 увеличивают интервалы, после получаса выясняют результат через поддержку. Численный общий лимит запросов в секунду на исследованной странице не опубликован — его нельзя придумывать. [Коды ответа](https://yookassa.ru/developers/using-api/response-handling/http-codes).

## 8. Чеки и проверка подключения

Для безопасной сделки документация описывает отдельные запросы чеков на **комиссию площадки до вычета эквайринга**. Для одностадийной оплаты чек создаётся после `succeeded`; при возврате собственной комиссии — чек возврата после успешного возврата. Используется сценарий «Сначала платеж, потом чек», а не поле `receipt` в запросе оплаты/возврата. Приём залога и выплата компенсации этой инструкцией не классифицированы. [Чеки в безопасной сделке](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/receipts).

Песочнице нужна тестовая интернет-площадка. Без сведений о компании для её подключения потребуется менеджер; тестовые возможности могут быть шире разрешённых боевому аккаунту. Тестируются карта и кошелёк ЮMoney, деньги не переводятся. Поэтому успешный тест не является договорным разрешением на обеспечение аренды залогом. [Тестирование безопасной сделки](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/testing).

До обещания полной интеграции заказчик должен получить ответы провайдера:

1. Допустимы ли аренда вещей между физлицами и **отдельная** сделка для реально списываемого возвратного залога?
2. Как сформировать оплату залога без дохода площадки и обеспечить `возврат + компенсация = весь залог`, включая компенсацию всей суммы? Какими именно балансами оплачиваются комиссии?
3. Каковы допустимые исходные `settlements` залога и последовательность частичного возврата/выплаты? Разрешены ли несколько выплат; существует ли поддерживаемое управление закрытием сделки?
4. Каков фактический срок хранения для этого подключения; можно ли завершить расчёт и что происходит при незавершённых payout/refund в момент истечения?
5. Какие проверки нужны обычному физлицу — резиденту РФ, допустима ли повторная выплата на новую карту после окончательного отказа в той же открытой сделке?
6. Как проводить суммы ниже минимальной выплаты/частичного возврата, какие документы и чеки нужны для залога и компенсации?
7. Каковы тарифы с налогами, минимальный резерв, лимиты API и условия доступа пилота к тестовому и боевому продуктам?

## Границы проверки

Проверены публичные инструкции, связанные официальные страницы и примеры запросов. [OpenAPI YAML](https://yookassa.ru/developers/api/yookassa-openapi-specification.yaml) объявлен официальной автоматически обновляемой схемой, но в этой среде не удалось прочитать его содержимое: веб-инструмент не поддержал тип файла, локальная загрузка не разрешила DNS. Динамический справочник показал только навигацию. Поэтому неподтверждённые параметры, включая `final_deal`, оставлены вопросами, а не дописаны по памяти. [Страница спецификации](https://yookassa.ru/developers/using-api/openapi-specification).

Не проверены доступы конкретного заказчика, реальные тарифы, договорное разрешение залога и полный сценарий в песочнице. Главный риск — запроектировать движение залога, которое провайдер технически или договорно не поддерживает.
