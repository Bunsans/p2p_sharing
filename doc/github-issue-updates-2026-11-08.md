## #2 Подтверждение продукта и проверка API провайдера

[Issue #2](https://github.com/Bunsans/p2p_sharing/issues/2)

Дополнить результаты исследования и список проверок:

- В Safe Deal используются `shopId` и секрет магазина, включая выплату внутри сделки; `account_id` виджета получателя также соответствует магазину. `agentId` и отдельный шлюз относятся к обычным выплатам. Не смешивать credentials и источники средств разных продуктов. [Пример Safe Deal](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/quick-start/freelance).
- Идемпотентность API гарантируется в течение 24 часов после первого запроса. После истечения окна нельзя автоматически повторять неизвестную операцию создания, даже с прежним ключом. Уточнить доступный способ поиска потерянной операции и обращения в поддержку. [Формат взаимодействия](https://yookassa.ru/developers/using-api/interaction-format).
- Успешная выплата закрывает сделку. Для частичной компенсации рассматривать последовательность «успешный возврат остатка → выплата компенсации», только после подтверждения провайдером. Эта последовательность не устраняет ограничение комиссий залога. Управление закрытием через `final_deal`/`final` не подтверждено доступными инструкциями. [Выплаты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payouts), [возвраты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/refunds).
- Проверить малые суммы: частичный возврат от 1 ₽, остаток после него — ноль или минимум 1 ₽; выплата на карту Safe Deal от 1 ₽. Нужен разрешённый порядок для результата 0,50 ₽ без самовольного округления. [Возвраты](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds), [выплаты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payouts).
- Уведомления подтверждаются HTTP 200; повторная доставка ограничена 24 часами. В списке есть `refund.succeeded`, но нет `refund.canceled`, поэтому отказ возврата нужно выяснять сверкой API. [Уведомления](https://yookassa.ru/developers/using-api/webhooks).
- Получить квоты по методам/учётной записи, правила 429, доступные лимиты сумм и способы оплаты, фактический срок сделки и поведение незавершённых refund/payout при его истечении. Публичные сведения не подтверждают конкретный допустимый RPS нашего подключения.

Дополнить критерии готовности:

- [ ] Записаны подтверждённые продукт, учётные записи, балансы для комиссий, лимиты и сроки именно подключения заказчика.
- [ ] Проверены полный возврат залога, частичная и полная компенсация без уменьшения сумм пользователям; определены параметры `settlements` и порядок операций.
- [ ] Проверены частичное исполнение и окончательный отказ выплаты, включая повтор на новые реквизиты в допустимой сделке.
- [ ] Определено, как разбирать неизвестную операцию без внешнего ID после окна идемпотентности.

Не повторять как новые открытия уже зафиксированные ограничения «одна успешная оплата на сделку», проблему нулевой наценки залога и необходимость специальной тестовой площадки. Уточнить их последствия указанными проверками.

## #3 Контракт команды и способ исполнения

[Issue #3](https://github.com/Bunsans/p2p_sharing/issues/3)

Добавить к проекту контракта следующие решения для согласования:

1. Общая PostgreSQL и короткие транзакции. Все пути, которым нужны связанные строки, соблюдают порядок блокировок «бронирование → расчёт → операции», включая Admin, уведомления и сверку. Выдача/отмена и сохранение соответствующей денежной команды согласуются атомарно; HTTP-вызов идёт после commit.
2. Сохранённая команда API с неизменным телом, ключом повтора и временем первой потенциальной отправки. Если очередь уже есть у команды — использовать её; иначе предложен исполнитель management command с очередью в БД. Решить supervision, расписание сверки и владельца эксплуатации.
3. Формат команд: доверенный автор, `command_id`, ожидаемая версия условий. Повтор с теми же данными возвращает существующий результат; тот же ключ с другими данными — конфликт. Суммы и получатель приходят из доверенного backend, а не из браузера.
4. Раздельный ответ для аренды, залога и выплаты: статусы, необходимые действия, ссылка подтверждения, версия и время обновления. Предложение: при создании команды HTTP 202 и ID, далее чтение состояния из нашей БД.
5. Гарантированная доставка денежных изменений основному backend: согласованный сервисный вызов в транзакции либо сохраняемое событие доставки. Один signal/callback без восстановления недостаточен.
6. Утвердить профиль нагрузочного теста и бюджеты ожидания. Предложения записки — p95 нашего API до 500 мс, получение задания до 1 с, connect timeout 3 с и общий deadline вызова 35 с — стартовые гипотезы, не SLA и не замеры. Утвердить частоту клиентского опроса и ограничение скорости API.

Уже открытые вопросы округления, нулевой следующей доплаты, поздней оплаты устаревшего продления и точек отсчёта 24/48 часов сохранить. Предлагаемое правило поздней оплаты — возврат неиспользованного до выплаты владельцу; зачёт в новое предложение требует отдельного решения. Записка не утверждает эту политику за команду.

Критерий: согласованы интерфейсы, общая транзакция, эксплуатация исполнителей и измеримые цели; приложены примеры успеха, повтора и конфликта версии. После этого можно оценивать готовность #5 независимо от завершения подключения провайдера.

- Для частично исполненного распределения залога определить ответственного и канал завершения обязательства: например, арендатор уже получил остаток, а компенсация владельцу отклонена. Успешный возврат не откатывается; новое исполнение не должно дублировать неизвестную выплату.
- Подтвердить по результатам #2 источники оплаты комиссий залога и необходимые средства площадки. Наличие баланса для возвратов не доказывает возможность оплатить из него комиссию выплаты полной компенсации.
- Уточнить подтверждение ручного исполнения: сумма, получатель, дата, внешний документ/референс, автор записи и ссылка на денежное решение. Решение и факт перевода учитываются раздельно.
- Подтвердить событие и данные чеков для принятой модели заказчика, а также отдельный порядок документов по залогу. Ошибка кассы не меняет состоявшуюся оплату на отказ.

Критерий: перечисленные обязательства и способы исполнения подтверждены заказчиком; провайдерские возможности подтверждены в #2. Архитектурное описание само по себе эти условия не закрывает.

## #5 Ядро, хранение и безопасное исполнение

[Issue #5](https://github.com/Bunsans/p2p_sharing/issues/5)

Дополнить реализацию после согласования #3:

- Разделить расчёт аренды, начисление, попытку оплаты, сделку, возврат, выплату, команду API, входящее событие, денежное решение/подтверждение, получателя и чек. Сохранять внутренние UUID и внешние непрозрачные ID с областью уникальности «провайдер/среда/учётная запись/тип».
- Деньги хранить в целых копейках, условия и исходящее тело фиксировать; чужой пользовательский ввод не определяет сумму операции. Финансовую историю не удалять каскадно.
- Команда создаётся в той же транзакции, что её основание. Сохранять `next_attempt_at`, счётчик попыток, lease и первую потенциальную отправку. Исполнитель захватывает задание короткой блокировкой; сетевой вызов выполняется вне транзакции. Повтор захвата означает ту же команду, а не новый ключ.
- `unknown` сохраняет открытой попытку и резерв. Повтор тела/ключа возможен только в гарантированном окне; после его истечения без установленного исхода автоматический POST останавливается. Запоздалый ответ старого исполнителя не откатывает подтверждённое состояние.
- Резервы возвратов и выплат считать по исходному платежу/сделке и назначению. Залог не покрывает расчёты аренды. Проверять исполненные и зарезервированные суммы под общей блокировкой расчёта.
- Сверка выбирает ограниченные пакеты по индексам статуса и срока, а не всю историю; очередь и неопределённые операции видимы в Admin. Секреты, токены и ссылки подтверждения не попадают в логи.

Дополнить проверками:

- [ ] Конкурирующие команды создают одну денежную операцию; повторные HTTP-запросы используют прежний ключ.
- [ ] Перезапуск после commit, потеря ответа и истечение lease не создают второй перевод.
- [ ] Неизвестная операция после 24 часов не запускается заново автоматически.
- [ ] Конкурирующие частичные возвраты не превышают остаток, резервы аренды и залога не смешиваются.
- [ ] Порядок блокировок и гонки проверены на PostgreSQL с независимыми соединениями.

Имитатор провайдера достаточен для проверок ядра, но не является приёмкой Safe Deal. Не добавлять зависимость #5 от #2 только из-за выбора клиента API.

## #6 Первый сквозной сценарий и уведомления

[Issue #6](https://github.com/Bunsans/p2p_sharing/issues/6)

Дополнить интеграционные требования:

- Использовать согласованный в #2 продукт и соответствующие credentials. В Safe Deal выплаты внутри сделки и виджет получателя используют магазин; отдельный шлюз обычных выплат не вводить автоматически.
- Сохранять `deal_id`, `payment_id`, `payout_id`, фактические сроки и суммы; аренда и залог имеют независимые результаты. Для выдачи нужны два подтверждённых `succeeded`, а не HTTP 200, `pending`, `paid` или переход по `return_url`.
- Webhook сохраняется до HTTP 200. Обработчик проверяет допустимый источник/формат, исполнитель сверяет актуальный объект в правильной учётной записи, связь, сумму, валюту и среду. Повторные события не повторяют денежные действия.
- Уведомление, пришедшее раньше ответа на POST, не теряется; запоздалое событие не понижает финальный статус. Периодическая сверка восстанавливает пропущенные результаты и продолжает отслеживать ещё открытую сделку.
- Начало выплаты связано с атомарно подтверждённой выдачей. Чтение состояния клиентом идёт из нашей БД и не создаёт отдельный GET к провайдеру на каждый опрос.

Критерий: успешный путь в специальной песочнице выбранного продукта, плюс повтор/потеря/опережение уведомления и потеря ответа API; нет двойной выплаты. Успех теста не заменяет разрешение боевого залога.

## #7 Частичный успех, отмена и возвраты

[Issue #7](https://github.com/Bunsans/p2p_sharing/issues/7)

Дополнить механизм возвратов и критерии:

- Сохранять отдельные объекты возврата и их резервы. Успешный возврат не меняет исходную оплату на `canceled`.
- Проверять отмену передачи и выдачу в согласованной общей транзакции. При отмене сохраняется намерение вернуть всё успешно принятое, включая оплату, обнаруженную после отмены.
- Отказ возврата выяснять сверкой: в опубликованном наборе webhook отсутствует `refund.canceled`. Timeout и HTTP 500 не освобождают резерв как при доказанном отказе.
- Для Safe Deal проверять доступность возврата до выплаты/закрытия, подтверждённый режим `fee_moment` и достаточность средств для расходов. Частичный возврат должен корректно уменьшать долю владельца через `deal.refund_settlements`.
- Использовать согласованное в #3 накопительное округление частичных возвратов: итог долей должен точно сходиться с первоначальными суммами. Ограничения API на малые суммы не обходить изменением согласованного итога.

Дополнительная приёмка: одновременные выдача/отмена, два частичных возврата, позднее списание после отмены, отсутствие webhook об отказе возврата, потерянный ответ возврата. В каждом случае сумма возвратов и резервов не превышает разрешённый остаток, состоявшиеся переводы учитываются ровно один раз.

## #8 Залог, споры и ручные корректировки

[Issue #8](https://github.com/Bunsans/p2p_sharing/issues/8)

Уточнить условие реализации: отдельный учёт залога не доказывает поддержку его исполнения Safe Deal. Включение реального списания залога зависит от решения #2 и условий #4; нельзя подменить бизнес-модель холдом или уменьшить компенсацию на комиссии.

Добавить требования:

- Состояния решения о распределении, возврата арендатору и компенсации владельцу независимы. Принимается одно версионированное решение с резервированием сумм; повтор решения не создаёт новые переводы.
- Для кандидата Safe Deal последовательность частичной компенсации — сначала подтверждённый возврат остатка, затем выплата; использовать её только после проверки в #2. Успешная выплата закрывает сделку. Сам порядок не решает вопрос финансирования комиссий при полном распределении залога.
- После успешного возврата и отказа/неизвестного исхода компенсации сохраняются выполненная часть и обязательство перед владельцем; неизвестная выплата не повторяется новым ключом.
- Малые суммы исполняются по согласованному правилу #2/#4, без самовольного округления.
- По фактическому `expires_at` следить за пределом сделки и незавершёнными операциями. Если провайдер вынужденно вернул залог, финансовое состояние обновляется, спор остаётся открытым; поздняя компенсация площадки учитывается отдельно.

Дополнить приёмку: полный возврат; компенсация части; компенсация всего залога; суммы ниже лимита; успешный возврат и неуспешная/неизвестная компенсация; повтор согласования; истечение сделки во время исполнения. В нормальном завершении `возврат арендатору + компенсация владельцу = залог`, а комиссии оплачивает площадка. Аварийная компенсация после вынужденного возврата отражается отдельным источником средств.

## #9 Продления, просрочка и долг

[Issue #9](https://github.com/Bunsans/p2p_sharing/issues/9)

Конкретизировать реализацию уже обозначенных сценариев:

- Доплата имеет своё начисление и версию предложения, отдельную попытку и, для кандидата Safe Deal, отдельную сделку. Она не переиспользует закрытую сделку первоначальной аренды и не запускает повторную выплату первоначальной суммы.
- Нулевой остаток за уже оплаченное покрытие не порождает нулевой банковский платёж; применяется согласованный контракт активации продления с согласия владельца.
- Поздний успех устаревшего предложения сохраняет денежный факт, но не меняет срок автоматически. Зачёт или возврат выполняется по согласованной в #3 политике. До её определения результат идёт на разбор; двойное начисление того же покрытия запрещено.
- При проверке продления использовать фактический срок отдельного залога, сохраняя ограничения 14 суток и семисуточного запаса. Неизвестный предельный срок не считается разрешением продлить аренду.

Дополнить приёмку: последовательные 10 + 10 минут без двойного округления; нулевая доплата; поздний успех старой версии; повтор уведомления доплаты; отказ отдельной выплаты по доплате. Неоплата времени не блокирует возврат залога при отсутствии претензий к вещи.
