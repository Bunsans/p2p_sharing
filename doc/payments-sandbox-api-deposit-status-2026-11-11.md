## Песочница: что именно предстоит проверить

У ЮKassa нужна **тестовая интернет-площадка для «Безопасной сделки»**. Она проводит операции через API без перемещения настоящих денег. По документации тестировать можно до договора, после регистрации и заполнения заявки. Если при регистрации не указаны данные компании, для этого продукта нужно обратиться к менеджеру. Используются идентификатор и ключ тестовой площадки; у созданных сделок, оплат и выплат будет `test: true`. Доступны тестовые оплаты картой и кошельком ЮMoney. [Официальная инструкция](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/testing).

Подготовка: создать тестовую площадку, настроить оплаты/выплаты и при необходимости проверку чеков, затем использовать специальные тестовые данные провайдера. Успешный тест не подтверждает разрешение того же сценария в production: тестовая площадка предоставляет возможности, которые для реальной могут требовать отдельного подключения. [Подготовка и ограничения](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/testing).

**Наш `--simulate` — локальная проверка.** [Simulator](../payments/simulator.py) выдаёт воспроизводимый `succeeded` с идентификатором `sim_…`, не обращаясь к ЮKassa. [Команда worker](../payments/management/commands/run_payment_worker.py) требует явного `--simulate`; [исполнитель](../payments/worker.py) ограничен `simulator/test/local`. Эти результаты не являются подтверждением приёмки в песочнице.

В репозитории ещё отсутствуют банковские HTTP-адаптеры, webhook, чеки и интеграция выдачи/отмены с основным backend. Следовательно, сейчас нельзя показать завершённую интеграцию с тестовой ЮKassa. Наличие доступа к кабинету отдельно не проверялось. [Текущий объём реализации](../README.md#что-реализовано).

## API: внешний провайдер и наш модуль

API ЮKassa использует `https://api.yookassa.ru/v3/`, JSON и HTTP Basic Auth. Для «Безопасной сделки» нужны `shopId` и секретный ключ магазина, в том числе при выплатах внутри сделки. Обычные выплаты со шлюза — другой вариант подключения. Для POST нужен `Idempotence-Key`: повтор операции сохраняет тело и ключ; гарантия повторения действует 24 часа. Сетевой сбой/HTTP 500 оставляет результат неизвестным до сверки. [Формат взаимодействия](https://yookassa.ru/developers/using-api/interaction-format).

| Объект ЮKassa | Создание и проверка | Для чего нужен |
| --- | --- | --- |
| Сделка | `POST /deals`, `GET /deals/{id}` | Связывает расчёты, хранит баланс и `expires_at`; состояния `opened` / `closed`. [Сделки](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/deals) |
| Оплата | `POST /payments`, `GET /payments/{id}` | Принимает деньги арендатора; `deal.id` связывает со сделкой, `settlements` задаёт долю владельца. [Оплаты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payments) |
| Возврат оплаты | `POST /refunds`, `GET /refunds/{id}` | Возвращает деньги по исходному `payment_id`; это отдельная операция. [Возвраты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/refunds) |
| Выплата владельцу | `POST /payouts`, `GET /payouts/{id}` | Перечисляет деньги владельцу; передаются `deal.id`, сумма и карточный токен из виджета. [Выплаты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payouts) |
| Чек | `POST /receipts` | Отдельный запрос на комиссию площадки до расходов провайдера; при возврате комиссии нужен чек возврата. [Чеки](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/receipts) |

Для реально списываемой оплаты используется `capture: true`. Состояние `waiting_for_capture` относится к двухстадийной оплате: это ещё ожидание списания. Выдачу вещи нельзя разрешать только по переходу пользователя на `return_url`; нужно подтверждённое состояние оплаты. [Процесс платежа](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process).

Результат узнают чтением объекта или уведомлениями. Для Basic Auth уведомления настраиваются в кабинете; обработчик должен проверять подлинность и выдерживать повторную доставку. События оплаты, выплаты, возврата и закрытия сделки относятся к разным объектам. [Уведомления](https://yookassa.ru/developers/using-api/webhooks).

Наши функции — внутренний контракт доверенного основного backend:

| Функция | Что делает сейчас |
| --- | --- |
| `prepare_settlement(...)` | Фиксирует условия и создаёт отдельные начисления аренды и залога |
| `start_payment(...)` | Ставит попытку оплаты в очередь; повтор команды возвращает прежнюю попытку |
| `reserve_money(...)` | Фиксирует одобренное денежное решение и резервирует суммы получателям |
| `start_outgoing(...)` | Ставит возврат или выплату по резерву в очередь локального исполнения |

Источники: [services.py](../payments/services.py), [reservations.py](../payments/reservations.py), [outgoing.py](../payments/outgoing.py). Здесь суммы хранятся в целых копейках; основной backend отвечает за полномочия участника и разрешение действия. Успешный вызов функции сам по себе не означает перевод денег. [Контракт подключения](../README.md#рабочий-контракт-подключения).

## Залог: рабочая модель и граница возможностей ЮKassa

По [ADR-0001](../docs/adr/0001-mvp-payment-scope.md) и [ADR-0003](../docs/adr/0003-cancellation-and-refunds.md) залог оплачивается отдельно от аренды с реальным списанием. Наценки площадки на залог нет. Без претензий возвращается вся сумма; при подтверждённом ущербе владелец получает компенсацию, арендатор — остаток. Все расходы провайдера оплачивает площадка. Долг за дополнительное время автоматически из залога не погашается.

Обычные физлица, не осуществляющие предпринимательскую деятельность, предусмотрены определением Сервиса безопасных расчётов; аренда прямо упомянута в помощи Safe Deal. Это сужает вопрос к провайдеру до нашего конкретного сценария: **отдельное списание обеспечительного платежа и последующая компенсация за ущерб**. Одобрение такой схемы из общего упоминания аренды не следует. [Правила ЮKassa](https://yoomoney.ru/document/pravila-raboti-servisa-yookassa), [способы оплаты](https://yookassa.ru/docs/support/safe-deal/accept-methods).

### Что подтверждено инструкциями и договорными правилами

1. **Одна сделка — один платёж в `pending`, `waiting_for_capture` или `succeeded`.** Повторное создание допускается после `canceled`. Поэтому независимые успешные оплаты аренды и залога не помещаются в одну сделку. [Оплаты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payments).
2. **Стандартная инструкция требует разницу между оплатой и `deal.settlements.amount` больше эквайринговой комиссии.** Провайдер удерживает её из вознаграждения площадки. Приём 3 000 ₽ с долей владельца 3 000 ₽ этому правилу не соответствует; договорную оговорку ниже нужно отдельно сопоставить с API. [Оплаты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payments).
3. **Успешная выплата закрывает сделку.** Возврат внутри неё доступен до выплаты/закрытия. Поэтому порядок «сначала компенсация владельцу, потом возврат остатка» не подходит опубликованному процессу. [Выплаты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payouts), [возвраты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/refunds).
4. **Полный возврат предусмотрен при `fee_moment=deal_closed`.** Невозвращаемые расходы эквайринга возмещаются с баланса магазина; при недостатке денег возврат не пройдёт. Это не доказывает возможность аналогично профинансировать выплату всего залога. [Возвраты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/refunds).
5. **Договор предусматривает покрытие недостающего вознаграждения оператора из обеспечения площадки.** Следующий абзац связывает срок удержания с запросом возврата. Это основание уточнить финансирование комиссии, но не готовое разрешение нулевой разницы или инструкция пополнения баланса сделки. [Приложение № 5, п. 6.11](https://yoomoney.ru/document/prilojenie-5). Общие правила допускают ограничения функций в зависимости от протокола: механизм нужно подтвердить именно для API v3. [Правила, п. 6.1.17](https://yoomoney.ru/document/pravila-raboti-servisa-yookassa).

Обеспечение площадки — её собственный пополняемый резерв; оно отличается от залога арендатора и от `deal.balance` / `deal.payout_balance`. Наличие резерва само по себе не означает, что API примет нужные суммы выплаты. [Баланс обеспечения](https://yookassa.ru/docs/support/safe-deal/balance), [балансы сделки](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/deals).

В инструкции выплат есть неясность: при `one_time_limit_exceeded` предлагается разбить сумму на несколько выплат, хотя успешная выплата описана как закрывающая сделку. Это не подтверждает несколько успешных выплат внутри одной сделки. Параметры `final_deal`/`final` для управления закрытием в проверенных инструкциях не найдены; отсутствие в инструкциях не доказывает отсутствие во всех вариантах API. До уточнения на эти варианты нельзя опираться. [Инструкция выплаты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payouts).

### Какие схемы остаются гипотезой

**Кандидат интеграции — отдельная сделка аренды и отдельная сделка залога.** Первую завершать выплатой при выдаче вещи, вторую — после возврата вещи или разрешения спора. Это вывод для проекта из ограничений выше, а не подтверждённое провайдером разрешение принимать обеспечительный залог. [Вопросы к ЮKassa, #2](https://github.com/Bunsans/p2p_sharing/issues/2).

| Залог 3 000 ₽ | Что известно | Что требуется подтвердить |
| --- | --- | --- |
| Претензий нет: возврат 3 000 ₽ | Полный возврат принятой оплаты описан в API | Разрешённый приём именно залога; баланс площадки для расходов |
| Ущерб 500 ₽: возврат 2 500 ₽ + выплата 500 ₽ | Кандидат порядка: дождаться успешного возврата остатка, затем выплатить компенсацию | Исходные `settlements`, последующие `refund_settlements` и источник расходов, сохраняющий обе суммы полностью |
| Ущерб 3 000 ₽: выплата всех 3 000 ₽ | Правило положительной разницы в API и договорное покрытие расходов ещё не согласованы между собой | Применимость п. 6.11 к этой выплате, настройки и точный запрос либо иной разрешённый расчёт |

Таблица — выводы исследования по [оплатам](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payments), [возвратам](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/refunds) и [договорным условиям](https://yoomoney.ru/document/prilojenie-5). **Просто принять залог отдельным платежом недостаточно: нужно доказать все три исхода.** Публичные документы не дают готового подтверждения всей модели, но и окончательный вывод о её невозможности пока не обоснован.

Порядок «возврат → выплата» сам по себе не устраняет нехватку денег. Если из залога `D` удержаны расходы `F`, после возврата `D − C` для компенсации `C` остаётся `C − F`. Нужно внешнее покрытие расходов. Например, при условных расходах 146,40 ₽ после приёма 3 000 ₽ и возврата 2 500 ₽ останется 353,60 ₽ вместо обещанных владельцу 500 ₽. Расчёт и его предпосылки разобраны в [исследовании](yookassa-deposit-feasibility-2026-11-11.md); это иллюстрация обычного движения баланса без внешнего покрытия, не тариф нашего договора.

### Что по залогу уже реализовано локально

`split_deposit(300_000, 50_000)` рассчитывает 50 000 копеек компенсации и 250 000 копеек возврата. `reserve_money(kind="deposit_distribution", amount_kopecks=50_000, ...)` атомарно резервирует обе части всего залога по успешной исходной оплате. При компенсации 0 или всего залога создаётся только ненулевой резерв. Повтор команды/основания возвращает прежнее решение. [Расчёты](../payments/calculations.py), [резервы](../payments/reservations.py).

Каждая ненулевая часть отдельно передаётся в `start_outgoing`. Сейчас это независимые локальные операции: **ожидание возврата залога перед выплатой компенсации не реализовано**. Резервы постоянные; пересмотр решений, освобождение резервов и ручные корректировки ещё не реализованы. Денежные обязательства уже можно учитывать, но завершённого банковского процесса залога нет. [Исходящие операции](../payments/outgoing.py), [worker](../payments/worker.py), [README](../README.md#денежные-решения-и-резервы).

## Сроки, мелкие суммы и договорные условия

Срок сделки задаётся при подключении; API-документация указывает 1–180 дней от создания сделки и описывает закрытие с возвратом остатка при истечении `expires_at`. Рабочий предел проекта — 14 суток от первой оплаты до планового возврата вещи плюс минимум 7 суток запаса до истечения сделки; проверять нужно фактический `expires_at`, учитывая создание сделки до оплаты. [Сделки](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/deals), [ADR-0002](../docs/adr/0002-payment-and-payout-timing.md).

**Продление возможно по договорной оговорке, но не гарантировано API.** Пункт 6.9 предусматривает согласованный при подключении возврат либо продление в пределах 180 дней, если площадка не направила запрос выплаты/возврата. Он не определяет судьбу уже принятой операции `pending` и не подтверждает наличие API-команды продления. [Приложение № 5, п. 6.9](https://yoomoney.ru/document/prilojenie-5). Спор сам по себе не подтверждает остановку срока: претензии участников разрешает площадка. [Соглашение СБР, п. 5.2.5–5.3](https://yoomoney.ru/document/soglashenie-o-servise-bezopasnix-raschetov).

**Найден потенциальный конфликт с ADR-0002.** Пункт 4.10 пользовательского соглашения связывает отказ в зачислении владельцу, например из-за закрытой карты, с возвратом арендатору. Не разъяснено, соответствует ли это любой попытке `canceled` или окончательной невозможности выплаты. Нужно согласовать границу допустимого повтора; рабочее правило «отказ сам по себе не запускает возврат» пока нельзя считать безусловно поддержанным провайдером. [Соглашение СБР, п. 4.10](https://yoomoney.ru/document/soglashenie-o-servise-bezopasnix-raschetov), [ADR-0002](../docs/adr/0002-payment-and-payout-timing.md).

Продуктовая страница при этом говорит о сроке до трёх месяцев и ориентире оборота от 800 000 ₽/месяц. Условия именно нашего пилота требуют ответа менеджера; ориентир не принимается за доказанный отказ в подключении. [Страница продукта](https://yookassa.ru/secure-deal/).

Минимум выплаты на карту — 1 ₽; частичного возврата — тоже 1 ₽, остаток после него должен быть нулём или не меньше 1 ₽. Учёт в копейках не снимает эти ограничения: компенсация/остаток 0,50 ₽ требуют отдельного согласованного способа исполнения. [Лимиты выплат](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payouts), [ограничения возвратов](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds).

Инструкция чеков описывает вознаграждение площадки, но не подтверждает налоговый порядок именно обеспечительного залога и компенсации. Найденное значение `payment_subject=lien` — фискальный реквизит, а не разрешение нашего сценария и не ответ, когда нужен чек. Налоговую модель, условия приёма залога и проверки владельцев ещё нужно согласовать. [Чеки ЮKassa](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/receipts), [значения реквизитов](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/other-services/parameters-values).

## Критические вопросы к провайдеру после исследования

| Вопрос | Какой ответ нужен для реализации |
| --- | --- |
| Покрытие комиссии при полной компенсации | Можно ли принять 3 000 ₽ с долей владельца 3 000 ₽ и выплатить её полностью, применив п. 6.11? Нужны настройки API v3, пример запроса и источник всех расходов |
| Частичная компенсация | Какие `settlements` и `refund_settlements` дадут ровно 2 500 ₽ арендатору и 500 ₽ владельцу? Как изменятся `balance` и `payout_balance`, когда закроется сделка? Как понимать рекомендацию нескольких выплат? |
| Предмет расчётов | Разрешены ли отдельный реально списанный залог без наценки и компенсация ущерба при аренде вещей между физлицами; какие условия договора и документы/чеки нужны? |
| Истечение и отказ выплаты | Что происходит с принятыми `pending`-операциями у `expires_at`, доступно ли договорное продление и когда отказ требует возврата по п. 4.10, а когда допустим повтор? |
| Подключение пилота | Доступен ли продукт при ожидаемом обороте заказчика; каковы фактические срок, тарифы, обеспечение, проверки получателя и допустимый канал компенсации после вынужденного возврата залога? |

Это оставшиеся вопросы для [#2](https://github.com/Bunsans/p2p_sharing/issues/2); готовых ответов провайдера в задаче на дату проверки нет. Отдельный продукт выплат от компании физлицу можно обсудить как запасной канал, но его собственный баланс и подключение не делают его автоматически разрешённой заменой расчётов Safe Deal. [Обычные выплаты](https://yookassa.ru/developers/payouts/overview).

## Следующая проверка, после которой можно говорить о реализуемости

1. **Получить конкретные ответы на таблицу выше в рамках [#2](https://github.com/Bunsans/p2p_sharing/issues/2).** Нужны допустимые суммы, параметры и договорное разрешение сценария. После ответа сверить рабочие ADR с условиями подключения, особенно правило отказа выплаты в ADR-0002.
2. **Подтвердить доступ и выполнить прототип в настоящей тестовой площадке** в рамках [#2](https://github.com/Bunsans/p2p_sharing/issues/2): `3 000 → возврат 3 000`, `3 000 → возврат 2 500 + выплата 500`, `3 000 → выплата 3 000`. Дополнительно проверить недостаток обеспечения, истечение при `pending` и отказ выплаты. Сохранить обезличенные запросы/ответы, ID объектов, статусы, `balance`, `payout_balance` и источник комиссий. Ответственного за подключение и резерв комиссий зафиксировать в [#4](https://github.com/Bunsans/p2p_sharing/issues/4).
3. **После подтверждения схемы реализовать интеграцию [#6](https://github.com/Bunsans/p2p_sharing/issues/6) и полный сценарий залога [#8](https://github.com/Bunsans/p2p_sharing/issues/8):** HTTP-адаптер и последовательность операций, сверку неизвестных исходов, уведомления и истечение срока. Проверить успех только одной из двух оплат, отмену до выдачи, неуспешный возврат/выплату и повторную доставку событий. Согласование с основным backend остаётся в [#3](https://github.com/Bunsans/p2p_sharing/issues/3).

Критерий результата: арендатор получает весь причитающийся возврат, владелец — всю компенсацию, площадка отдельно покрывает расходы; повторы и сбои не меняют согласованный денежный итог. Пока нет такого подтверждения и разрешения провайдера, обещать готовность полного залога к запуску нельзя.

## Границы этой проверки

При проверке 11 ноября изучены публичные инструкции и договорные документы ЮKassa/ЮMoney, исходники и состояние GitHub Issues. При первоначальной проверке выполнены 20 тестов арифметики: `python3 -m unittest tests.test_calculations -v`, все прошли. Это не тесты банковской интеграции. При обновлении этой сводки тесты приложения повторно не запускались; код и ADR не менялись.

Динамический [справочник API](https://yookassa.ru/developers/api) в инструменте показал только навигацию; [OpenAPI YAML](https://yookassa.ru/developers/api/yookassa-openapi-specification.yaml) не прочитан из-за неподдерживаемого типа ответа. Поэтому полная схема API и неподтверждённые флаги не объявлены проверенными.

Не проверены кабинет и секреты заказчика, индивидуальные тарифы/договор и реальные операции API. Главный оставшийся риск — финансовый сценарий залога, который стандартная «Безопасная сделка» или условия конкретного подключения могут не поддерживать.
