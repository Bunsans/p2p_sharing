# ЮKassa: повторная проверка отдельного залога

Дата проверки: **11 ноября 2026 года**. Первичные источники: API-инструкции, официальная помощь и договорные документы ЮKassa/ЮMoney.

**Полный возврат принятой оплаты документирован. Для выплаты всего залога и распределения 2 500 ₽ / 500 ₽ найдено договорное основание уточнить оплату комиссии площадкой, но готовая схема API по-прежнему не подтверждена. Обычные физлица предусмотрены условиями сервиса; аренда прямо упомянута в справке. Отдельный обеспечительный залог и компенсация за ущерб остаются предметом согласования.**

Исследование уточняет [предыдущую сводку](payments-sandbox-api-deposit-status-2026-11-11.md) и рабочую модель [ADR-0001](../docs/adr/0001-mvp-payment-scope.md)–[ADR-0003](../docs/adr/0003-cancellation-and-refunds.md). Это проверка опубликованных возможностей, а не приёмка интеграции или индивидуального договора.

| Критический вопрос | Что теперь можно ответить | Что ещё не подтверждено |
| --- | --- | --- |
| Вернуть все 3 000 ₽ без наценки | Механизм полного возврата есть; расходы несёт площадка | Разрешение принимать именно залог, доступ и достаточный резерв |
| Выплатить владельцу все 3 000 ₽ | Есть расхождение договорного механизма расходов и инструкции API | Приём `amount=settlement`, источник комиссии и допустимость выплаты всей суммы |
| Вернуть 2 500 ₽ и выплатить 500 ₽ | Возврат должен предшествовать успешной выплате; одной последовательности недостаточно | Точные `refund_settlements`, остаток для выплаты и покрытие комиссии |
| Аренда между обычными физлицами | Физлица предусмотрены договорной моделью, аренда названа в помощи | Отдельный обеспечительный платёж и выплата компенсации |
| Срок, спор, незавершённые операции | Известны API-срок и дополнительное договорное условие продления | Гонка истечения с `pending`, окончательный отказ выплаты и возможность продления конкретного подключения |

Основания и границы каждого ответа приведены ниже.

## Что изменилось относительно предыдущей проверки

1. Найдена специальная договорная база: **раздел 6 Приложения № 5**, а также пользовательское соглашение Сервиса безопасных расчётов (СБР). Раньше выводы опирались главным образом на инструкции API.
2. Выявлено, что вопрос финансирования комиссии нельзя закрыть утверждением «баланс обеспечения существует только для возвратов»: договорную оговорку необходимо сопоставить с настройками API.
3. Найдены прямое упоминание аренды, условия для обычных физлиц и дополнительная договорная оговорка о сроке. Это сужает оставшиеся вопросы к провайдеру.
4. Обнаружено условие об окончательной невозможности выплаты, которое нужно сверить с рабочим решением ADR-0002.

## 1. Полный возврат и полная выплата — разные проверки

При `fee_moment=deal_closed` инструкция предусматривает полный возврат оплаты, включая ранее удержанные расходы эквайринга за счёт баланса магазина. При недостатке денег возврат не выполнится; после успеха сделка закрывается, а её баланс может быть отрицательным. Для оплаты 3 000 ₽ этот механизм означает возврат 3 000 ₽, если исходный платёж принят допустимым способом. [API: возвраты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/refunds).

Справка отдельно объясняет создание **баланса обеспечения**: его открывают через менеджера и пополняют с расчётного счёта организации из договора. Это деньги площадки для обеспечения её обязательств; их нельзя смешивать с залогом арендатора. [Баланс обеспечения](https://yookassa.ru/docs/support/safe-deal/balance).

Для полной выплаты возникает другое ограничение: инструкция требует, чтобы разница между оплатой и `deal.settlements.amount` превышала эквайринговую комиссию. Поэтому запрос с оплатой 3 000 ₽ и предназначенной владельцу суммой 3 000 ₽ не соответствует опубликованному правилу. [API: приём оплаты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payments).

**Новая договорная зацепка:** п. 6.11 предусматривает удержание недостающего вознаграждения оператора из обеспечения площадки. Следующий абзац связывает срок удержания с запросом возврата. Это не описание разрешённой выплаты при нулевой разнице и не инструкция пополнения баланса сделки. [Приложение № 5, п. 6.11](https://yoomoney.ru/document/prilojenie-5).

Вывод: **нельзя ни обещать выплату всех 3 000 ₽, ни объявлять её окончательно невозможной**. Нужен ответ, как договорное условие реализуется при таком платеже: настройкой магазина, особым тарифом, другим расчётом или никак. Наличие резерва само по себе не доказывает, что API допустит нужные суммы.

Пункт 6.1.17 общих Правил прямо допускает ограничения функциональности в зависимости от протокола интеграции. Поэтому договорный механизм нужно подтвердить именно для используемого API v3. [Правила ЮKassa](https://yoomoney.ru/document/pravila-raboti-servisa-yookassa).

| Денежный объект | Его документированное назначение |
| --- | --- |
| `deal.balance` | Баланс конкретной сделки; при `deal_closed` обычный расчёт учитывает удержанную комиссию и НДС. [Приём оплаты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payments) |
| `deal.payout_balance` | Учёт причитающейся владельцу части; это не обещание выплаты независимо от фактического баланса. [Проведение сделки](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/deals) |
| Баланс обеспечения площадки | Отдельно пополняемое обеспечение; готовый API-переход «перенести деньги в залоговую сделку» в проверенных инструкциях не найден. [Помощь](https://yookassa.ru/docs/support/safe-deal/balance) |

## 2. Распределение 3 000 ₽ → 2 500 ₽ + 500 ₽

Для частичного возврата передаются общая возвращаемая сумма и данные об уменьшении доли владельца. После возврата должно остаться достаточно денег для выплаты. Успешная выплата закрывает сделку, поэтому кандидат последовательности — **успешный возврат остатка, затем выплата компенсации**. [API: частичный возврат](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/refunds), [API: выплата](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payouts).

В той же инструкции выплат для ошибки `one_time_limit_exceeded` предлагается разбить сумму на несколько выплат. Как это сочетается с закрытием после успешной выплаты, не объясняется. Эта рекомендация не подтверждает несколько успешных выплат в одной сделке; допустимый порядок также требует уточнения. [Причины отмены выплаты](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payouts).

Проверка арифметики показывает, почему этого порядка недостаточно. Пусть `D` — принятый залог, `C` — компенсация, `F > 0` — удержанные расходы приёма, включая НДС. Если внешнего покрытия нет:

```text
Баланс после оплаты:                  D − F
Возврат арендатору:                   D − C
Остаток для компенсации:              C − F
Не хватает до обещанной компенсации:  F
```

Это вывод для обычного движения баланса, а не доказательство запрета индивидуальной схемы. Публичная инструкция описывает внешнее возмещение расходов при полном возврате; для частичного исхода готовый механизм сохранения обеих сумм целиком не установлен. [Расчёт баланса](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payments), [условия возврата](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/refunds).

Например, справочная карточная ставка для оборота до 1 млн ₽ — 4% без НДС; инструкция учитывает НДС 22% на комиссию. При таких условных ставках приём 3 000 ₽ стоит 146,40 ₽, после возврата 2 500 ₽ остаётся 353,60 ₽. До выплаты 500 ₽ недостаёт 146,40 ₽. **Это иллюстрация, не тариф нашего договора.** [Тарифы Safe Deal](https://yookassa.ru/docs/support/safe-deal/fees), [комиссии и НДС](https://yookassa.ru/docs/support/safe-deal/rewarding).

Не следует подбирать произвольное `refund_settlements`, чтобы формально получить нужный остаток: нужно подтвердить и сохранение полного возврата, и право владельца на 500 ₽, и источник расходов. Снижение исходной доли владельца также не доказывает возможность позже выплатить все 3 000 ₽ при полной утрате вещи.

Отдельные оплаты аренды и залога требуют раздельных расчётов: в одной сделке допускается только один платёж в `pending`, `waiting_for_capture` или `succeeded`. Две сделки остаются кандидатом интеграции, а не разрешением принимать залог. [Ограничение платежей](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payments).

## 3. Физлица, аренда и обеспечительный залог

**Обычные физлица — подтверждённая категория участников.** В общих Правилах СБР определён как сервис для физлиц, не осуществляющих предпринимательскую деятельность; пользовательское соглашение отдельно определяет физических лиц — участников сделки. Наличие ИП/ООО у оператора площадки не превращает владельцев в предпринимателей. [Правила ЮKassa, определения](https://yoomoney.ru/document/pravila-raboti-servisa-yookassa), [пользовательское соглашение, раздел 2](https://yoomoney.ru/document/soglashenie-o-servise-bezopasnix-raschetov).

**Аренда прямо названа в помощи Safe Deal** среди сервисов, которым полезна привязка карты для регулярных платежей: «такси, аренда и подобные». Это подтверждает применимость продукта к аренде как классу сценариев, но не одобрение нашей разновидности аренды или автосписаний. [Способы оплаты и получения денег](https://yookassa.ru/docs/support/safe-deal/accept-methods).

**Приём именно отдельного обеспечительного залога не подтверждён.** Пользовательское соглашение описывает расчёты за товар/работу/услугу и вознаграждение площадки. В проверенных правилах не найден сценарий «возвратный залог, затем компенсация за ущерб»; такую компенсацию нельзя без согласования назвать ценой услуги. [Соглашение СБР, определения и раздел 4](https://yoomoney.ru/document/soglashenie-o-servise-bezopasnix-raschetov).

В справочнике чеков действительно есть `payment_subject=lien` — залог. Это значение фискального реквизита, а не разрешение использовать Safe Deal для нашего обеспечительного платежа и не ответ, когда нужен чек. Налоговую модель отдельного залога эта находка не подтверждает. [Справочник реквизитов чеков](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/other-services/parameters-values).

Требуется согласовать конкретное описание: аренда вещей между физлицами, отдельное реальное списание без наценки, возврат при отсутствии претензий, компенсация по соглашению сторон либо решению администратора, расходы площадки. Существующая формулировка залога в [глоссарии](../GLOSSARY.md) сохраняется.

## 4. Срок, спор и незавершённые операции

API-инструкция задаёт срок жизни сделки **1–180 дней**, устанавливаемый при подключении для всех сделок площадки. Срок начинается с создания сделки; фактическую границу нужно читать из `expires_at`. При истечении документировано закрытие и возврат оставшихся средств. Рекламное «до трёх месяцев» не заменяет параметры подключения. [Проведение сделки](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/deals), [страница продукта](https://yookassa.ru/secure-deal/).

**Дополнительное условие:** п. 6.9 допускает согласованное при заключении договора продление вместо возврата, в пределах 180 дней. Условие сформулировано для случая, когда площадка не направила запрос выплаты/возврата. Оно не устанавливает исход уже принятой операции `pending`. [Приложение № 5, п. 6.9](https://yoomoney.ru/document/prilojenie-5).

Спор разрешает площадка: провайдер не рассматривает взаимные претензии участников аренды. Поэтому наличие спора само по себе не доказывает остановку срока сделки. Наши 14 суток аренды, семь суток запаса и предупреждения за 72/24 часа остаются внутренними ограничениями, которые нужно сверять с фактическим сроком. [Соглашение СБР, п. 5.2.5–5.3](https://yoomoney.ru/document/soglashenie-o-servise-bezopasnix-raschetov), [ADR-0002](../docs/adr/0002-payment-and-payout-timing.md).

| Состояние у `expires_at` | Что подтверждено | Что нельзя обещать |
| --- | --- | --- |
| Операции не начаты, деньги остались | Общая API-схема предусматривает возврат остатка | Автоматическое продление именно нашего подключения |
| Возврат уже `pending` | Возврат — отдельная операция со своим итоговым статусом | Немедленный успех, отмену или продолжение только по факту закрытия сделки |
| Выплата уже `pending` | Исход выплаты ещё не подтверждён | Что истечение отменит выплату либо обязательно позволит ей закончиться |
| Выплата `canceled` | Причина доступна; для некоторых причин инструкция предлагает сменить средство получения | Что любую отменённую попытку провайдер считает окончательной невозможностью |

Последние три исхода не описаны исчерпывающе в проверенных инструкциях о жизненном цикле. Нужна согласованная таблица переходов и испытание соответствующей гонки. [Возвраты](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds), [выплаты и причины отмены](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/integration/payouts).

**Потенциальный конфликт с ADR-0002:** п. 4.10 пользовательского соглашения связывает отказ в зачислении владельцу, например из-за закрытой карты, с возвратом арендатору. Соответствие этого отказа статусу отдельной попытки `canceled` не разъясняется. Нужно определить границу между исправимой попыткой и окончательным отказом; рабочее правило «отказ сам по себе не запускает возврат» нельзя считать безусловно согласованным. [Соглашение СБР, п. 4.10](https://yoomoney.ru/document/soglashenie-o-servise-bezopasnix-raschetov).

## Подключение пилота и возможный отдельный канал

Ориентир **от 800 000 ₽/месяц** опубликован на странице продукта. Найденная таблица ставок «до 1 млн ₽» не доказывает подключение ниже 800 000 ₽. Публичного обещания подключения нашего пилота или доказанного жёсткого отказа по этому порогу не найдено. [Продукт](https://yookassa.ru/secure-deal/), [тарифы](https://yookassa.ru/docs/support/safe-deal/fees).

Для подключения нужны договор, проверка площадки и обеспечение. На сайте должны быть реквизиты оператора, описание услуг, публичная оферта и правила оплаты/возвратов. Тестирование возможно до подписания договора после регистрации и заявки; регистрация без данных компании не даёт такой же самостоятельный доступ к Safe Deal. Успех в тестовом режиме не подтверждает разрешение возможностей в боевом подключении. [Подключение](https://yookassa.ru/docs/support/safe-deal/onboarding), [подготовка площадки](https://yookassa.ru/docs/support/safe-deal/arrangement), [тестирование](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/testing).

У ЮKassa есть отдельный продукт выплат от компании физлицу: собственный баланс, отдельное подключение, комиссия списывается сверх перечисляемой суммы. Его можно обсудить как канал компенсации из средств площадки, в том числе после вынужденного возврата залога. Но документация отделяет этот продукт от выплат внутри Safe Deal: наличие такого API **не разрешает автоматически** перенести туда расчёты залога. [Обычные выплаты](https://yookassa.ru/developers/payouts/overview).

## Конкретные оставшиеся вопросы провайдеру

1. **Договор и API комиссии:** разрешается ли при `fee_moment=deal_closed` принять 3 000 ₽, указать `settlements=3 000 ₽` и выплатить их целиком, списав все расходы с площадки? Как применить п. 6.11 при требовании положительной разницы в инструкции? Нужны настройки и пример запроса.
2. **Частичный исход:** какие исходные `settlements` и последующие `refund_settlements` дают ровно 2 500 ₽ арендатору и 500 ₽ владельцу? Как меняются оба баланса, откуда списываются комиссия и НДС, когда закрывается сделка? Допускаются ли несколько успешных выплат в одной сделке, несмотря на описанное закрытие после выплаты?
3. **Предмет расчётов:** допустимы ли отдельный реально списанный обеспечительный платёж и компенсация за ущерб для аренды вещей между обычными физлицами? Какая формулировка нужна в договоре площадки и какие документы/чеки требуются?
4. **Истечение и отказ:** что происходит с принятыми `pending`-возвратом/выплатой при `expires_at`; можно ли договорно продлевать залоговую сделку; когда применяется п. 4.10, а когда допустим повтор выплаты?
5. **Пилот:** доступен ли продукт при ожидаемом обороте заказчика; каковы фактический срок, тарифы, обеспечение и разрешённый аварийный канал компенсации после возврата залога?

Это вопросы по найденным расхождениям и отсутствующим параметрам. Само наличие `refund` и `payout` уже не является достаточным ответом.

## Что должна доказать песочница после согласования

| Проверка | Критерий результата |
| --- | --- |
| Полный возврат | Арендатору 3 000 ₽; расходы отдельно у площадки; сделка закрыта |
| Частичная компенсация | Возврат 2 500 ₽ подтверждён, владельцу выплачено 500 ₽; источник всех расходов виден |
| Полная компенсация | Владельцу выплачено 3 000 ₽; расходы не уменьшают эту сумму |
| Недостаток обеспечения | Понятный отказ и восстановление после пополнения без повторного перечисления |
| Истечение при `pending` | Известен итог исходной операции и автоматического возврата; нет двойного исполнения |
| Отказ выплаты | Подтверждены допустимый повтор, граница окончательного отказа и последствия для залога |

Сохранять нужно обезличенные запросы/ответы, статусы, идентификаторы, `balance`, `payout_balance` и фактическое списание расходов. API-проверка не заменяет договорное разрешение обеспечительного платежа. [Возможности и ограничения тестового режима](https://yookassa.ru/developers/solutions-for-platforms/safe-deal/testing).

## Границы проверки

Прочитаны официальная помощь, API-инструкции, общие Правила, специальный раздел СБР и пользовательское соглашение. Поиск по словам «аренда», «залог», «обеспечительный платёж», «компенсация», `pending` и `expires_at` не дал отдельного опубликованного процесса нашего залога. Отсутствие найденного процесса не считается запретом.

Полная актуальная OpenAPI-схема и текущие исходники SDK не прочитаны: web-инструмент не раскрыл YAML, локальная загрузка ограничена сетью, новый официальный хостинг SDK отдал только оболочку. Архивные GitHub SDK не использованы как доказательство актуального API. Флаги `final`/`final_deal` остаются неподтверждёнными. [OpenAPI](https://yookassa.ru/developers/api/yookassa-openapi-specification.yaml), [официальные SDK](https://yookassa.ru/developers/using-api/using-sdks).

Запросы к платёжному API, кабинет заказчика, индивидуальный договор и поддержка не использовались. Числовой пример проверен вычислением с Decimal и утверждениями; код приложения и ADR не менялись, банковские тесты не запускались. Главный риск — подтвердить арифметику локально, но не получить разрешённый способ исполнить те же суммы у провайдера.
